# 002 — SSO: OIDC (Google / Microsoft / custom) + SAML

## Current state (before this spec)

- Local email/password auth only (bcrypt + JWT). No provider abstraction, no
  IdP integration, no JIT provisioning.

## Requirements

- Provider abstraction supporting local passwords AND external IdPs.
- OIDC via **authlib** (no hand-rolled crypto): Google, Microsoft Entra ID,
  and any discovery-URL IdP (Okta OIDC etc.).
- SAML 2.0 config surface; runtime requires `python3-saml` (native xmlsec
  deps) — scaffolded behind an optional import.
- `SSOConfig` per account: provider_type, discovery/metadata, client creds,
  domain restriction, `enforced` flag, JIT default role.
- `enforced=true` → password login rejected for that domain; login page
  auto-redirects to IdP.
- Global "Sign in with Google / Microsoft" buttons (OIDC direct) for EXISTING
  users (matched by verified email) even without per-account SSO.

## Data model

| Table | Columns |
|-------|---------|
| `sso_configs` | id, tenant_id, provider_type(oidc/saml), name, discovery_url, client_id, client_secret, metadata_xml, email_domain, default_role_name, enforced, enabled, created_at, updated_at |

## API surface

```
GET  /sso/options                     global providers configured (google/microsoft)
GET  /sso/lookup?email=               {sso_required, login_url} by domain
GET  /sso/{slug}/login                302 to IdP (slug = account slug | google | microsoft)
GET  /sso/{slug}/callback             validate, JIT-provision, 302 to editor with token pair in #fragment
GET/POST/PATCH/DELETE /accounts/{id}/sso   (manage_settings) config CRUD + "test connection"
```

## Flow decisions

- `state` param = signed JWT (10 min) carrying slug + CSRF nonce; verified on
  callback. ID token verified against the IdP JWKS via authlib.
- JIT provisioning: user created with `email_verified=true`, membership +
  `default_role_name` assignment (default EDITOR) — only when the email domain
  matches `email_domain` (or no restriction).
- Global google/microsoft: **no** JIT account creation — the verified email
  must already belong to a user; otherwise 403 with guidance to sign up.
- Tokens are handed to the SPA via URL fragment (`/login#access=…&refresh=…`)
  so they never hit server logs.
