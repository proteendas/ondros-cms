# CLI

`ondros-cli` — a zero-dependency Node CLI for the management API. Source in
[`cli/`](../cli). Requires Node 18+ (it uses the built-in `fetch`).

Its real job is keeping content models in version control and generating
TypeScript types from them, so your frontend breaks at compile time when the
model changes rather than at runtime in production.

## Install

```bash
npm install -g ondros-cli
# or, from a checkout
node cli/bin/ondros-cli.mjs --help
```

## Commands

| Command | Purpose |
|---|---|
| `login` | Authenticate and store a session |
| `spaces` | List spaces with environments and locales |
| `types export` | Dump content types to JSON |
| `types import` | Apply content types from JSON |
| `generate-types` | Emit TypeScript definitions for your model |

### `login`

```bash
ondros-cli login --host http://localhost:8000 \
  --email admin@example.com --password admin123
# ✓ Logged in to http://localhost:8000 as admin@example.com (account 29bcee20…)
```

Stores host plus the access/refresh pair in an rc file. The CLI refreshes
automatically on a `401`, and tells you to log in again if the refresh token
has also expired.

> The password appears in your shell history. On a shared machine, prefer a
> `cms_mgm_…` key, or clear the history line afterwards.

### `spaces`

```bash
ondros-cli spaces
# ba300ee4…  Marketing Site (marketing)  envs: [master]  locales: [en-US, fr]
```

Mostly used to find the space id the other commands need.

### `types export`

```bash
ondros-cli types export --space <spaceId> --env master -o content-model.json
```

Exports `name`, `api_id`, `description`, `display_field` and `fields` — the
portable parts. Ids, timestamps and environment references are dropped, so the
file applies cleanly to any environment. Omit `-o` to print to stdout.

**Commit this file.** It turns your content model into reviewable code: schema
changes show up in pull requests as a diff.

### `types import`

```bash
ondros-cli types import --space <spaceId> --env staging -i content-model.json
```

Matches on `api_id` — existing types are updated, new ones created. Nothing is
deleted, so a type missing from the file is left alone rather than destroying
its entries.

Promoting a model between environments:

```bash
ondros-cli types export --space $SPACE --env master  -o model.json
ondros-cli types import --space $SPACE --env staging -i model.json
```

Review [the safe/unsafe change table](08-content-modeling.md#evolving-a-schema-safely)
before importing into an environment that already has content — adding a
`required` field will fail validation on the next publish of existing entries.

### `generate-types`

```bash
ondros-cli generate-types --space <spaceId> --env master -o src/cms-types.d.ts
```

Emits an interface per content type, with a header marking it generated:

```ts
/* Generated by ondros-cli from space ba300ee4… (master) — do not edit. */

export interface LandingPage {
  title: string;
  hero?: string;           // reference — an entry id
  cards?: string[];        // reference_many
  body?: unknown;          // richtext — ProseMirror JSON
}
```

Reference fields type as `string` because that is what the API returns — an
id. Resolve them via the SDK's `resolve()` / `resolveLinks()`
([14-sdk.md](14-sdk.md)).

Re-run it whenever the model changes; in CI, run it and fail if the output
differs from the committed file, which catches a model change that nobody
propagated to the frontend.

## Typical workflows

**Model in version control**

```bash
ondros-cli types export --space $SPACE --env master -o content-model.json
git add content-model.json && git commit -m "chore: sync content model"
```

**Promote to production**

```bash
ondros-cli types import --space $PROD_SPACE --env master -i content-model.json
ondros-cli generate-types --space $PROD_SPACE --env master -o src/cms-types.d.ts
```

**CI drift check**

```bash
ondros-cli generate-types --space $SPACE --env master -o /tmp/types.d.ts
diff -q /tmp/types.d.ts src/cms-types.d.ts \
  || { echo "Content model changed — regenerate types"; exit 1; }
```

## Notes

- Everything goes through the **management plane**, so the session needs the
  matching capabilities — `manage_content_types` to import.
- `--env` defaults to `master`.
- Import is additive by design. Deleting a content type is destructive and is
  left to the UI or API, where the consequences are explicit.
